# External API Module — Payments/PSP Orchestration Platform (`nexxus` brand service)

## 1. Overview

The platform exposes **two distinct external surfaces**, both living in the `brand` service (`fynxt.brand.*`) and both sitting behind the global API prefix **`/nexxus/v1`** (applied by `SecurityConfig.webMvcConfigurer` → `PathMatchConfigurer.addPathPrefix`):

| Surface | Package | Path root | Consumer | Purpose |
|---|---|---|---|---|
| **Inbound PSP callback API** | `fynxt.brand.external` | `/nexxus/v1/external/**` | The **PSP / acquirer** (and end-user browser) | Receives redirect returns and server-to-server webhooks *from* payment providers after the platform kicked off a flow. Public, token-in-URL. |
| **Merchant/integrator API** | `fynxt.brand.request`, `fynxt.brand.transaction` | `/nexxus/v1/requests/**`, `/nexxus/v1/transactions/**` | The **merchant/integrator** (server-side) | Fetch available PSPs + fees, create/track transactions. Authenticated with `X-SECRET-TOKEN`. |
| **Outbound webhook delivery** | `fynxt.brand.webhook` | (config API `/nexxus/v1/webhooks/**` + async delivery) | Merchant's server (receiver) | Platform *sends* transaction result notifications out to the merchant. |

Terminology warning — "webhook" is overloaded:
- `/external/inbound/w/...` = **inbound** webhooks the platform *receives from PSPs*.
- The `webhook/` package = **outbound** webhooks the platform *sends to merchants*.

### How this differs from the internal admin API
Internal admin/config controllers are `@RequiresScope({"FI","BRAND"})` + `@RequiresPermission(...)`, authenticated with a **JWT Bearer** token plus `X-BRAND-ID` / `X-ENV-ID` headers and RBAC checks. The external surfaces bypass RBAC:
- `/external/**` is fully **public** (no auth filter); trust derives from the unguessable environment `token` UUID embedded in the URL.
- `/requests/**` is `@RequiresScope({"EXTERNAL"})` and reached via `X-SECRET-TOKEN`, whose strategy sets `bypass.permission.check=true`, disabling `@RequiresPermission`/`@RequiresScope` enforcement.

## 2. Authentication & Security

There is **no HMAC request signing, no per-request signature header, no nonce/replay protection, and no IP allowlist** anywhere in the external surfaces. Authentication is entirely **bearer-secret style** using opaque UUIDs. The security filter chain is `SecurityConfig.customSecurityFilterChain` (CSRF disabled, `STATELESS` sessions).

### 2.1 Auth strategies (chain order)
`AccessTokenOncePerRequestFilter` runs first-matching of three ordered `AuthenticationStrategy` beans:

| Order | Strategy | Trigger header | Validation |
|---|---|---|---|
| 0 | `AdminTokenAuthenticationStrategy` | `X-ADMIN-TOKEN` | admin-token-paths |
| 1 | `SecretTokenAuthenticationStrategy` | `X-SECRET-TOKEN` | UUID → `EnvironmentLookupService.findBySecret(secret)`; sets request attrs `environment`, `auth_type=SECRET_TOKEN`, `bypass.permission.check=true`; grants `ROLE_SECRET` |
| 2 | `JwtAuthenticationStrategy` | `Authorization: Bearer <jwt>` | issuer/audience/kid + DB active-token check; `token_type` must be `ACCESS` |

Route classification comes from `application-routes.yml` (`fynxt.auth.route.*`):
- **public-paths** (permitAll, no auth): `/nexxus/v1/external/**`, `/nexxus/v1/auth/**`, `/nexxus/v1/sessions/**`, `/nexxus/v1/health/**`, swagger, `/db-scheduler/**`.
- **secret-token-paths** (`X-SECRET-TOKEN`): `/nexxus/v1/requests/**`, `/nexxus/v1/transactions/**`, `/nexxus/v1/webhooks/**`, `/nexxus/v1/psps/**`, `/nexxus/v1/fees/**`, and other flow/rule config paths.
- **brand-env-paths** (`X-BRAND-ID` + `X-ENV-ID`, FI/BRAND scope + JWT): same config paths for internal console use.

### 2.2 The inbound `/external/**` authentication model
These endpoints are **public**. The security control is the **environment `token`** (a UUID) baked into the URL path. In `ExternalServiceImpl.read`:
1. `environmentService.readByToken(UUID.fromString(token))` → 404 `ENVIRONMENT_NOT_FOUND` if unknown.
2. `transactionService.read(tnxId)` → 404 `TRANSACTION_NOT_FOUND` if unknown.
3. Cross-check: `environment.id == transaction.environmentId` **and** `environment.brandId == transaction.brandId`; else 400 `TRANSACTION_VALIDATION_FAILED`.

A caller must know both a valid environment token **and** a matching transaction id. These callback URLs are generated by the platform itself and handed to the PSP (`VMExecuteImpl.buildDenoVMUrls`):
- redirect: `{backendServerUrl}{prefix}/external/inbound/r/redirect/{token}/{transactionId}`
- webhook: `{backendServerUrl}{prefix}/external/inbound/w/webhook/{token}/{transactionId}`

CORS: **open** (`allowedOriginPattern="*"`, `allowCredentials=false`) for any URI containing `/external/`; locked-down (frontend URL only, credentials allowed) for everything else.

### 2.3 Merchant API (`/requests`) authentication
`X-SECRET-TOKEN: <environment-secret-UUID>` → resolved to an environment; brand/env read from `BrandEnvironmentContextHolder`. Client IP captured from `X-Forwarded-For` (first hop) → `X-Real-IP` → `remoteAddr` (used for risk rules, not access control). Environment secrets can be rotated (`EnvironmentService.rotateSecret`).

### 2.4 Credential handling
- PSP credentials stored encrypted (`Psp.credential` JSON), decrypted per-call via `CryptoUtil.decryptCredentialJsonNode`; failure → 500 `TOKEN_DECRYPTION_FAILED`.
- `CredentialSanitizer` scrubs credential values out of DenoVM `error`/`meta` (replaces with `**ENCRYPTED**`). Sanitizing of the `data` field is **commented out** in `VMExecuteImpl.sanitizeDenoVMResult`, so only `error`/`meta` are sanitized.
- Session-token binding uses `HmacSHA256` with hard-coded key `"binding-key-fynxt-nexxus-token-system"` — JWT session infra, **not** applied to external request/webhook signing.

## 3. REST API Endpoints

### 3.1 `ExternalController` — inbound PSP callbacks (`@RequestMapping("/external")`, public)
`token` = environment UUID; `tnxId` = transaction id. All `@PathVariable`s `@NotBlank`. `r` path returns a browser 302 redirect; `w` path returns JSON `ApiResponse`.

| Method | Full path (with prefix) | Returns | Handler |
|---|---|---|---|
| POST | `/nexxus/v1/external/inbound/r/{step}/{token}/{tnxId}` | `RedirectView` (302) | `handleReadPost` |
| POST | `/nexxus/v1/external/inbound/r/{step}/{token}` | `RedirectView` (302) | `handleReadPostNoTnxId` (txnId from body/query) |
| GET | `/nexxus/v1/external/inbound/r/{step}/{token}/{tnxId}` | `RedirectView` (302) | `handleReadGet` |
| GET | `/nexxus/v1/external/inbound/r/{step}/{token}` | `RedirectView` (302) | `handleReadGetNoTnxId` |
| POST | `/nexxus/v1/external/inbound/w/{step}/{token}/{tnxId}` | `ApiResponse<Object>` | `handleWritePost` |
| POST | `/nexxus/v1/external/inbound/w/{step}/{token}` | `ApiResponse<Object>` | `handleWritePostNoTnxId` |
| GET | `/nexxus/v1/external/inbound/w/{step}/{token}/{tnxId}` | `ApiResponse<Object>` | `handleWriteGet` |
| GET | `/nexxus/v1/external/inbound/w/{step}/{token}` | `ApiResponse<Object>` | `handleWriteGetNoTnxId` |

Request processing pipeline (`ExternalRequestExtractor` → `ExternalRequestMapper` → `ExternalRequestHandler` → `ExternalServiceImpl` → `VMExecuteImpl`):
- `RequestBodyExtractor` parses `application/x-www-form-urlencoded` and `application/json` (all parse failures swallowed → empty map); `extractRawBody` uses `ContentCachingRequestWrapper` (populated by `RawBodyCachingFilter`).
- `extractTransactionId` recursively scans query then body for a value starting with the transaction prefix; `cleanTransactionId` URL-decodes and strips `?...`.
- For `r` (redirect): `extractRedirectUrl` pulls `data.url` (must start with `http://`/`https://`/`/`); if absent, falls back to environment `origin`. Always HTTP 302.

There is **no DTO** on this controller — the request is an untyped `Map<String,Object>`. The typed `VmExecutionDto` (builder: `pspId`, `token`, `flowTargetId`, `@Positive Long amount`, `currency`, `brandId`, `environmentId`, `step`, `flowActionId`, `transactionId`, `executePayload`) is built internally in `ExternalServiceImpl.read`.

### 3.2 `RequestController` — merchant PSP discovery (`@RequestMapping("/requests")`, `@RequiresScope({"EXTERNAL"})`)

| Method | Full path | Request DTO | Response |
|---|---|---|---|
| POST | `/nexxus/v1/requests/fetch-psp` | `RequestInputDto` | `ApiResponse<RequestOutputDto>` |

`RequestInputDto` (validated): `amount` `@NotNull @Positive BigDecimal`, `currency` `@NotBlank`, `actionId` `@NotBlank`, `country` `@NotBlank`, `customerId` `@NotBlank`, `customerTag` `@NotBlank`, `customerAccountType` `@NotBlank`. `brandId`/`environmentId`/`clientIpAddress` server-set. Missing brand/env context → 400 `MISSING_REQUIRED_PARAMETER`.

`RequestServiceImpl.fetchPsp` (transactional): saves a `Request`, resolves eligible PSPs (`PspResolutionService`), computes fees once (`FeeCalculationService`), persists `RequestPsp`/`RequestFee`/`RequestRiskRule`/`RequestTransactionLimit`, returns `RequestOutputDto{ requestId, psps[] }`. Each `PspInfo`: id/name/logo, `flowActionId`, `flowDefintionId`, `originalAmount`, fee breakdown (`appliedFeeAmount`, `totalAmount`, `netAmountToUser`, `inclusiveFeeAmount`, `exclusiveFeeAmount`, `isFeeApplied`), `flowTarget{ flowTargetId, inputSchema }`.

### 3.3 `TransactionFlowController` — merchant transaction lifecycle (`@RequestMapping("/transactions")`)
See the Transaction module doc. Summary:

| Method | Full path | Auth notes |
|---|---|---|
| POST | `/nexxus/v1/transactions` | brand/env from context → `createTransactionWithSession` → `TransactionResponseDto` |
| PUT | `/nexxus/v1/transactions/{txnId}/status?status={TransactionStatus}` | `@RequiresPermission(transactions, update)` |
| GET | `/nexxus/v1/transactions/{txnId}` | `@RequiresPermission(transactions, read)` |
| GET | `/nexxus/v1/transactions/{txnId}/status` | (no permission annotation) |
| POST | `/nexxus/v1/transactions/search` | `@RequiresPermission(transactions, read)`; paginated |

### 3.4 `WebhookController` — outbound-webhook configuration CRUD (`@RequestMapping("/webhooks")`, `@RequiresScope({"FI","BRAND"})`)
Standard CRUD, each `@RequiresPermission(module="webhooks", action=...)`, brand/env via headers: `POST /webhooks`, `GET /webhooks`, `GET /webhooks/{id}`, `PUT /webhooks/{id}`, `DELETE /webhooks/{id}`. `WebhookExecutionService.getWebhookStats` / `getWebhookLogs` exist in the service layer but are **not exposed** by any controller.

## 4. Webhooks (outbound delivery — `fynxt.brand.webhook`)

Recently migrated to **db-scheduler** (`com.github.kagkarlsson.scheduler`).

### 4.1 Configuration entity (`Webhook`, table `webhooks`)
`id Short` (SMALLSERIAL), `statusType` (PG enum `webhook_status_type`), `url`, `retry Integer` (default 3), `brandId`, `environmentId`, `status` (`ENABLED`/`DISABLED`), `apiKey`. Uniqueness per `(brandId, environmentId, statusType)` — duplicate create → `DUPLICATE_RESOURCE` / HTTP 409. Soft-delete + restore.

`WebhookDto` validation: `statusType @NotNull`; `url @NotBlank @Pattern(^https?://.*)`; `retry @Min(0) @Max(10)` (default 3); `apiKey` sent as `x-api-key` header in webhook requests.

### 4.2 Event types (`WebhookStatusType`): `SUCCESS`, `FAILURE`, `NOTIFICATION`
Chosen in `ExternalServiceImpl.determineWebhookStatusType`:
- step `redirect` → `SUCCESS` if `vmResponse.data != null` else `FAILURE`
- step `webhook` → `NOTIFICATION`

Delivery fanned out to **all enabled webhooks** matching `(brandId, environmentId, statusType, ENABLED)`, or a single webhook if `webhookId` supplied.

### 4.3 Outbound payload structure (`ExternalServiceImpl.createWebhookPayload`)
```json
{
  "transactionId":     "<txn id>",
  "brandId":           "<uuid>",
  "environmentId":     "<uuid>",
  "pspId":             "<uuid>",
  "flowActionId":      "<string>",
  "externalRequestId": "<string>",
  "step":              "redirect | webhook",
  "timestamp":         "<epoch millis>",
  "response":          "<DenoVMResult.data or null>"
}
```

### 4.4 Outbound HTTP request (`WebhookHttpClient`)
`RestTemplate` with `SimpleClientHttpRequestFactory`, **connect timeout 5000 ms, read timeout 30000 ms**. Always `POST`, `Content-Type: application/json`. Only header added is **`x-api-key: <apiKey>`** when apiKey non-blank, else none. Success = HTTP 2xx.

### 4.5 Signing / replay protection — GAP
Outbound webhooks are **not signed**. No HMAC signature header, no timestamp-signature, no body digest — only an optional static `x-api-key`. The `timestamp` in the payload is informational and not part of any signature, so receivers cannot verify authenticity or protect against replay.

### 4.6 Delivery, retry, and logging (`WebhookExecutionServiceImpl` + `WebhookJob`)
- Enqueue: builds `WebhookJob.Payload{ webhookId, payloadJson, correlationId, attempt, maxRetries }` → `schedulerClient.scheduleIfNotExists(...)`. Instance id = `"webhook-{id}-{correlationId}-{attempt}"` (idempotent per attempt). `correlationId` = transaction id.
- Execute (`WebhookJob.execute`, `OneTimeJobHandler`): loads webhook; if `DISABLED` writes `CANCELLED` log; else HTTP call, records timing/status/response, sets `SUCCESS` on 2xx else `RETRIED` (more attempts remain) or `FAILED`, persists a `WebhookLog`, rethrows on failure to trigger failure handler.
- Retry (`WebhookJob.onFailure`): if `attempt < maxRetries`, schedules attempt+1. Delay = `INITIAL_DELAY(60s) * 2^attempt` then **capped at `MAX_RETRY_DELAY_SECONDS = 60`** → effectively a flat ~60 s between retries (the exponential factor is nullified by the cap — likely a bug).
- `WebhookLog` (`webhook_logs`): `webhookId`, `responseStatus`, `isSuccess`, `requestPayload`/`responsePayload`/`responseHeaders` (JSONB), `errorMessage`, `executionTimeMs`, `attemptNumber`, `executionStatus` (PG enum: `PENDING`, `IN_PROGRESS`, `SUCCESS`, `FAILED`, `RETRIED`, `CANCELLED`), `scheduledAt`/`executedAt`/`completedAt`/`retryAfter`, `jobId`, `correlationId`, `userAgent`, `contentType`.
- Stats: `WebhookLogRepository.getSuccessRateStats` → `WebhookStatsResult.Stats | NotFound` (service only, no endpoint).

## 5. Validations & Error Responses

### 5.1 Inbound `/external` request validation
- Path vars `token`/`tnxId`/`step` `@NotBlank`.
- Env/txn existence + brand/env cross-match (§2.2): `ENVIRONMENT_NOT_FOUND` (404), `TRANSACTION_NOT_FOUND` (404), `TRANSACTION_VALIDATION_FAILED` (400).
- PSP/operation must be enabled: `PspService.getPspIfEnabled`, `PspOperationsService.getPspOperationIfEnabled`.
- Any processing exception → 500.

### 5.2 JSON-Schema validation of DenoVM I/O (`VMExecuteImpl` + `JsonSchemaAndPayloadValidator`)
- Uses `com.networknt.schema` **JSON Schema Draft V7**.
- **Input** validated against `flowAction.inputSchema[step]` before executing.
- **Output** validated against `flowAction.outputSchema[step]` only on success and non-failure type.
- `extractStepSchemaJson` selects the sub-schema for the current step, forces `additionalProperties=true`. Missing step schema → `DenoVMResult.error(...)`.
- On mismatch: `AppException(VALIDATION_ERROR, BAD_REQUEST)` `"Schema validation failed: ..."`, returned as `DenoVMResult.error(...)`.
- Failure detection: DenoVM `data.__type`/`data._type == "failure"` (case-insensitive) → treated as failure.

### 5.3 Merchant `/requests` validation
Bean-validation on `RequestInputDto` (§3.2). Missing auth context → 400 `MISSING_REQUIRED_PARAMETER`.

### 5.4 Auth errors (from strategies)
`AUTHENTICATION_REQUIRED` (401), `SECRET_TOKEN_INVALID` (401), `TOKEN_VALIDATION_FAILED` (401, JWT), `AUTHENTICATION_FAILED` (500). Bodies via `ErrorResponseUtil.writeErrorResponse`.

### 5.5 Webhook config validation
DTO constraints (§4.1) + duplicate `(brand, env, statusType)` → 409; not found → `RESOURCE_NOT_FOUND` (404).

## 6. End-to-End Use Case — Merchant payment + webhook callback

1. **Discover PSPs.** Merchant server → `POST /nexxus/v1/requests/fetch-psp` with `X-SECRET-TOKEN: <env-secret>` and body `{amount, currency, actionId, country, customerId, customerTag, customerAccountType}`. Secret resolves the environment (brand+env context); `RequestServiceImpl.fetchPsp` persists a `Request`, resolves eligible PSPs, computes fees, returns `{ requestId, psps:[{id, flowActionId, flowDefintionId, totalAmount, flowTarget{flowTargetId, inputSchema}, ...}] }`.

2. **Create transaction.** Merchant picks a PSP → `POST /nexxus/v1/transactions` (`TransactionDto`, secret-token auth) → `createTransactionWithSession` mints a transaction (`txnId`) and returns `TransactionResponseDto` (session/redirect info).

3. **Flow execution → PSP.** Orchestrator runs the flow step in the **Deno VM** (`VMExecuteImpl.executeDenoVm`), passing decrypted PSP credentials, the payload, and platform-generated callback URLs in `DenoVMRequest.urls.server`:
   - redirect: `…/external/inbound/r/redirect/{token}/{txnId}`
   - webhook: `…/external/inbound/w/webhook/{token}/{txnId}`
   (`origin` URLs = environment success/failure redirect URLs.) The PSP returns a hosted-payment `data.url`.

4. **User pays at PSP**, then PSP **returns the browser** to `GET/POST /nexxus/v1/external/inbound/r/redirect/{token}/{txnId}` (public). `ExternalServiceImpl.read` validates env↔txn, re-runs the VM for `step=redirect`, advances the flow (`executeNextStep`), then responds **302** to `data.url` if present, else environment `origin`.

5. **PSP async confirmation** → `POST /nexxus/v1/external/inbound/w/webhook/{token}/{txnId}` (server-to-server). Same validation + VM run for `step=webhook`; returns JSON `ApiResponse` "Success".

6. **Platform → Merchant outbound webhook.** After each step, `ExternalServiceImpl.sendWebhookAfterTransaction` builds the payload (§4.3), picks `SUCCESS`/`FAILURE`/`NOTIFICATION`, and `WebhookExecutionService.sendWebhook` enqueues a db-scheduler `WebhookJob` per matching enabled `Webhook`. `WebhookJob.execute` POSTs the JSON to the merchant's configured `url` with optional `x-api-key`, logs in `webhook_logs`, and on non-2xx/timeout schedules retries (attempt < `retry`, ~60 s spacing) ending in `FAILED` or `RETRIED`/`SUCCESS`. `correlationId` = `txnId`.

### Frontend
- Outbound-webhook management UI: `frontend/src/pages/configuration/tabs/webhook/` (`webhook-form.tsx`, `webhook-modal.tsx`, `webhook-list.tsx`, `webhook-columns.tsx`, `hooks/use-webhook-form.ts`, route `routes/configuration/webhook.tsx`). API: `api/services/webhook.service.ts` (CRUD; headers auto-injected; explicit 409-conflict toast). Zod `webhook.validation.ts`: `statusType ∈ {SUCCESS,FAILURE,NOTIFICATION}`, `url` valid http(s) ≤500, `retry ∈ {"1","2","3"}` (stricter than backend 0–10), `status ∈ {ENABLED,DISABLED}`, optional `apiKey`.
- There is **no dedicated external "API key management" page** — external credentials are the environment **secret** (rotated via `EnvironmentService.rotateSecret`) and the per-webhook `apiKey` field.

## 7. Key findings / risks
- **No signing or replay protection on either direction.** Inbound `/external` trusts an in-URL environment token; outbound webhooks carry at most a static `x-api-key` and an unsigned `timestamp`. Consider HMAC-signing outbound payloads and verifying inbound PSP callbacks.
- **Retry backoff is effectively flat ~60 s** (`WebhookJob`): `INITIAL_DELAY=60s * 2^attempt` capped at `MAX_RETRY_DELAY_SECONDS=60` neutralizes the exponential curve — almost certainly unintended.
- **DenoVM `data` is not credential-sanitized** on the response path (only `error`/`meta` are) — the sanitization call is commented out.
- **Silent parse failures** in `RequestBodyExtractor` (all exceptions → empty map) can mask malformed inbound callbacks.
- Frontend limits `retry` to 1–3 while backend allows 0–10 — a mismatch.
