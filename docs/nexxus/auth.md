# Authentication, Authorization, Session & Permission Subsystem — Nexxus Brand Service

## 1. Overview

Nexxus is a multi-tenant payments platform. The `brand` service (`fynxt.brand`) implements auth on top of three shared Spring Boot auto-configuration libraries:

| Lib | Package | Responsibility |
|-----|---------|----------------|
| `libs/jwt` | `fynxt.jwt` | Stateless JWT generation & validation (JJWT, HMAC-SHA) |
| `libs/auth` | `fynxt.auth` | Spring Security filter chain, pluggable authentication strategies, CORS, route classification |
| `libs/permission` | `fynxt.permission` | AOP-based RBAC — `@RequiresScope` / `@RequiresPermission` aspects |

Architecture summary:

- **Authentication** is credential-based (email + password). On success the server issues a JWT **access token** (1h) + **refresh token** (7d), both persisted as HMAC hashes in a `tokens` table for revocation/introspection. Tokens are **stateless JWTs** but backed by a DB "active" check → a hybrid (stateful revocation over stateless tokens).
- **Authorization** is scope + role based. Every JWT carries a `scope` (`FI`, `BRAND`, `EXTERNAL`). `FI`/`EXTERNAL` scopes are unrestricted; `BRAND` scope users are gated by per-role JSON permission maps stored on `brand_roles.permission` (jsonb). Enforcement is via AOP aspects on controllers.
- **Sessions** (`sessions` table) are an unrelated concept — short-lived *transaction* sessions for hosted-payment flows, not login sessions. Login state is stateless JWT (`SessionCreationPolicy.STATELESS`).
- **Three auth mechanisms** coexist, selected by request headers: `X-ADMIN-TOKEN` (super-bypass), `X-SECRET-TOKEN` (environment machine auth), and `Authorization: Bearer` (JWT user auth).

Key source locations:
- Controller: `backend/services/brand/src/main/java/fynxt/brand/auth/controller/AuthController.java`
- Core service: `.../auth/service/impl/AuthServiceImpl.java`
- Filter chain: `backend/libs/auth/src/main/java/fynxt/auth/filter/AccessTokenOncePerRequestFilter.java`
- Strategies: `backend/libs/auth/src/main/java/fynxt/auth/strategy/`
- Frontend interceptor: `frontend/src/api/auth-interceptor.ts`, store: `frontend/src/store/auth.store.ts`

## 2. Authentication Flow

### 2.1 Endpoints (`AuthController`, base `/auth`)

| Method | Path | Body / Params | Returns |
|--------|------|---------------|---------|
| POST | `/auth/login` | `LoginRequest` JSON `{email, password}` | `201` + `AuthResponse`, message `"Login successful"` |
| POST | `/auth/token/refresh` | `@RequestParam refreshToken` (query param) | `201` + `AuthResponse`, `"Token refreshed successfully"` |
| POST | `/auth/logout` | Header `Authorization: Bearer <token>` | `200`/deleted + `"Logout successful"` |

All responses wrapped by `ResponseBuilder` into `ApiResponse<Object>` (envelope: `timestamp`, `code`, `message`, `data`). Success code `"0000"` (frontend also accepts `"200"`).

### 2.2 Login — step by step (`AuthServiceImpl.login`)

1. `userAuthService.authenticateUser(email, password)` — `BrandUserAuthenticationServiceImpl`:
   - `userService.findByEmailForAuthentication(email)` → loads `User` from `users`; `401 USER_NOT_FOUND (1035)` if absent.
   - `validateUserPassword`: `cryptoUtil.decrypt(user.getPassword())` then `password.equals(decryptedPassword)`. **Passwords are stored reversibly encrypted (AES/GCM), not hashed.** Mismatch/decrypt error → `401 AUTH_INVALID_CREDENTIALS (1011)`.
   - `buildUserInfo`: determines scope. `fiService.findByUserId` first → scope = **`FI`** (map includes `fiId`, `fiName`, `brands[]`). Else `brandUserService.findByUserId` → scope = **`BRAND`** (map includes `accessibleBrands[]` with per-environment `roleId`). Neither → `403 USER_NO_ACCESS (1038)`.
   - Returns `Map` with `userId, email, scope, status, authType="INTERNAL", fiId, fiName, brands, accessibleBrands`.
2. Null user/userId → `401 AUTH_INVALID_CREDENTIALS`.
3. Generate access token + refresh token.
4. `tokenManagementService.cleanupExpiredTokensForUser(userId)` — marks user's expired ACTIVE tokens `EXPIRED`.
5. `saveTokens(access, refresh, userId)` — persists both token hashes.
6. Build `AuthResponse`. On `JwtTokenGenerationException`/`JwtSigningKeyException` → `500 TOKEN_ISSUANCE_FAILED (1039)`.

### 2.3 JWT structure

Generated by `JwtExecutorImpl.generateToken` (JJWT `Jwts.builder()`, `signWith(HMAC key)`).

**Standard claims:** `iss`, `sub` (= userId string), `aud`, `exp`, `iat`.

**Access-token custom claims** (`buildUserAccessTokenClaims`):

| Claim | Source | Notes |
|-------|--------|-------|
| `auth_type` | `APPLICATION_USER` | always for user login |
| `token_type` | `ACCESS` | |
| `scope` | `FI` / `BRAND` | drives RBAC |
| `user_id` | Integer | |
| `email` | user email | |
| `fi_id`, `fi_name` | if FI user | |
| `brands` | if FI user | list of `{id,name,environments[{id,name}]}` |
| `accessible_brands` | if BRAND user | list of `{id,name,environments[{id,name,roleId}]}` |

**Refresh-token claims:** `auth_type`, `token_type=REFRESH`, `user_id`, `scope`.

**Signing:** HMAC key derived per key-id via `getSigningKey(keyId)` = `Base64(SHA-256("jwt-signing-key-" + keyId + "-fynxt-token-system"))`. Access and refresh use **different key ids** (`jwt.signing-key-id` vs `jwt.refresh-signing-key-id`).

**Expiry** (`JwtProperties`, prefix `jwt`): `access-token-expiration` default `PT1H`; `refresh-token-expiration` default `P7D`. Also `issuer`, `audience`.

### 2.4 Refresh flow (`AuthServiceImpl.refreshToken`)

1. `validateRefreshToken`: validates JWT with the **refresh** signing key; must be valid, `token_type == REFRESH`, and `tokenValidationService.isRefreshTokenActive(refreshToken, subject)` (DB check). Failure → `401 TOKEN_VALIDATION_FAILED (1040)`.
2. Only `auth_type == APPLICATION_USER` supported; reloads user via `getUserInfoById(userId)` and mints a **new access token** (fresh claims from current DB state).
3. `revokeAccessTokensForUser(subject)` then `saveToken(newAccessToken)`. The **same refresh token is returned** (not rotated).

### 2.5 Logout (`AuthServiceImpl.logout`)

Strips `"Bearer "`, extracts `user_id` (validating with access signing key), then `revokeAllTokensForUser(userId)` (all ACTIVE → `REVOKED`).

### 2.6 Filter chain (order)

`SecurityConfig` (`@EnableWebSecurity`, CSRF disabled, `STATELESS`):

1. `CorsFilter` (`HIGHEST_PRECEDENCE`). Open CORS for `/external/`; else credentialed CORS limited to `fynxt.auth.frontend-url`.
2. `RawBodyCachingFilter`.
3. `CorrelationIdWebFilter` — reads/generates `X-Correlation-ID`.
4. `AccessTokenOncePerRequestFilter` — the auth gate.
5. `BrandEnvironmentContextFilter` `@Order(100)` — populates the RBAC thread-local **after** authentication.

**`AccessTokenOncePerRequestFilter.doFilterInternal`:**
1. If `routeConfig.isPublic(uri)` → pass through.
2. Else pick first `AuthenticationStrategy` whose `canHandle(request)` is true (ordered by `@Order`).
3. None → `401 AUTHENTICATION_REQUIRED (1013)`.
4. `strategy.validate(...)` — on false the strategy has already written the error response.

**Strategies:**

| Order | Class | Trigger | On success |
|-------|-------|---------|-----------|
| 0 | `AdminTokenAuthenticationStrategy` | `X-ADMIN-TOKEN` (admin-token path) | compares to `fynxt.auth.admin-token`; sets `bypass.permission.check=true`, `ROLE_ADMIN`. Invalid → `401 INVALID_TOKEN (1014)` |
| 1 | `SecretTokenAuthenticationStrategy` | `X-SECRET-TOKEN` (secret-token path) | UUID → `environmentLookupService.findBySecret`; sets attrs `environment`, `auth_type=SECRET_TOKEN`, `bypass.permission.check=true`, `ROLE_SECRET`. Invalid → `401 SECRET_TOKEN_INVALID (1015)` |
| 2 | `JwtAuthenticationStrategy` | `Authorization: Bearer` | full JWT validation (below) |

**`JwtAuthenticationStrategy.validate`:** requires Bearer prefix; validates via `JwtExecutor` (access issuer/audience/signing-key); `token_type` must be `ACCESS`; subject non-blank; `tokenValidationService.isAccessTokenActive(token, subject)` DB check (inactive → mark EXPIRED and reject). Failure → `401 TOKEN_VALIDATION_FAILED (1040)` (or `500 AUTHENTICATION_FAILED (1016)` if JWT config missing). Success sets request attributes **`jwt.subject`, `jwt.claims`, `jwt.token`** and a Spring auth token with `ROLE_AUTHENTICATED`.

`RouteConfig` (`fynxt.auth.route.*`, `AntPathMatcher`): arrays `publicPaths`, `brandEnvPaths`, `adminTokenPaths`, `secretTokenPaths`; `isJwtRequired = !isPublic`.

## 3. Authorization / RBAC

### 3.1 Scope model (`fynxt.common.enums.Scope`)
`FI`, `BRAND`, `EXTERNAL`. (Frontend `auth.store.ts` uses `"SYSTEM" | "BRAND" | "FI"` — `SYSTEM` maps loosely to the FI/internal concept client-side.)

### 3.2 Two AOP aspects (`libs/permission`)

Both consult `PermissionContextHolder`, implemented by `BrandEnvironmentContextHolder` (delegates to a thread-local).

**`@RequiresScope` (`ScopeCheckAspect`, `@Order(1)`, class-level `@within`):**
- Bypassed if request attr `bypass.permission.check` (admin/secret tokens).
- Reads `contextHolder.getScope()`; null → `PermissionDeniedException("Authentication required - no scope found")`.
- Requires user scope ∈ annotation `value()`; else `PermissionDeniedException("Access denied - scope '<scope>' not allowed")`.

**`@RequiresPermission(module, action)` (`PermissionCheckAspect`, `@Order(2)`, method-level `@annotation`):**
- `PermissionServiceImpl.hasPermission(module, action)`:
  - Bypass flag → `true`.
  - Scope `FI` or `EXTERNAL` → `true` (no permission gating).
  - Scope `BRAND` → `validateBrandPermission`: reads `contextHolder.getRolePermissions()` (`Map<String,Object>`), navigates `rolePermissions[module].actions` (`List<String>`), checks `contains(action)`.
  - else `false`.
- On false → `PermissionDeniedException("You don't have permission to '<action>' on '<module>' module")`.

`PermissionDeniedException` → `ErrorCode.AUTH_INSUFFICIENT_PERMISSIONS (1012)`, category `FORBIDDEN` → HTTP 403.

### 3.3 How `BRAND` permissions get loaded (`BrandEnvironmentContextFilter`, `@Order(100)`)

Runs after authentication. Reads `jwt.claims` + `jwt.subject` request attributes, builds a `BrandEnvironmentContext` (thread-local, cleared in `finally`):
- `scope`, `authType`, `fiId`, `customerId`, `userId` from claims.
- **`brandId`/`environmentId`:** prefers request headers **`X-BRAND-ID`** / **`X-ENV-ID`**, falling back to claims `brand_id`/`environment_id`.
- `resolveRoleId`: walks `accessible_brands` (or `brands`) claim structure (`BrandClaimStructureParsing`) to find the `roleId` for the selected brand+environment.
- `rolePermissions = brandRoleService.getRolePermissions(roleId)` → deserializes `brand_roles.permission` jsonb into a `Map`.
- For secret-token requests builds a minimal context from the `environment` attribute.

So **brand-scoped permission = (JWT identity) × (X-BRAND-ID/X-ENV-ID selected tenant) × (role's JSON permission map)**. A user can hold different roles per environment.

### 3.4 Permission catalog (`resources/static/permissions.json`, served by `GET /permissions/modules`)

| Module | Actions |
|--------|---------|
| `brand_roles` | create, read, update, delete |
| `brand_users` | create, read, update, delete |
| `fees` | create, read, update, delete |
| `psp_groups` | create, read, update, delete |
| `psps` | create, read, update |

Stored role permission shape (jsonb): `{ "<module>": { "actions": ["read","create",...] }, ... }`.

### 3.5 Spring authorities
Coarse-grained: `ROLE_AUTHENTICATED` (JWT), `ROLE_ADMIN` (admin token), `ROLE_SECRET` (secret token). Fine-grained authorization is entirely the aspect layer, not Spring `hasRole`.

## 4. Session Management

**(a) Login session** — none. `STATELESS`; identity lives in the JWT + `tokens` table.

**(b) Token store (`tokens` table)** — `fynxt.brand.auth.entity.Token`:

| Column | Type | Notes |
|--------|------|-------|
| `id` | bigint identity | |
| `customer_id` | String | = userId string |
| `token_hash` | varchar(500), unique | HMAC-SHA256 of `token|customerId|expiresAtUTC` using binding key |
| `issued_at`, `expires_at` | OffsetDateTime | UTC, truncated to seconds |
| `status` | pg enum `token_status` | `ACTIVE` / `EXPIRED` / `REVOKED` |
| `token_type` | pg enum `token_type` | `ACCESS` / `REFRESH` |

`TokenManagementServiceImpl`:
- **Hash binding key**: `Base64(SHA-256("binding-key-fynxt-nexxus-token-system"))` — the raw JWT is never stored, only an HMAC.
- Lifecycle: `saveTokens`/`saveToken`; `revokeAllTokensForUser`, `revokeAccessTokensForUser`, `revokeRefreshTokensForUser` (→ `REVOKED`); `cleanupExpiredTokensForUser` / `updateExpiredTokenStatus` (→ `EXPIRED`); `isAccessTokenActive` / `isRefreshTokenActive` via `countActiveToken`.
- `TokenRepository`: `findByTokenHash`, `findActiveByCustomerId`, `findActiveByCustomerIdAndTokenType`, `countActiveToken`, `findExpiredTokens`.

**(c) Transaction session (`sessions` table)** — `fynxt.brand.session.entity.Session` (payment-flow, not auth):

| Column | Notes |
|--------|-------|
| `brand_id`, `environment_id` | UUID |
| `txn_id`, `txn_version` | transaction key |
| `session_token_hash` | varchar(512), HMAC-SHA256 of session token via `cryptoProperties.hmacKey()` |
| `expires_at` | Instant; default timeout 5 min (or ceil(pspTimeoutSeconds/60)) |
| `last_accessed_at`, `timeout_minutes` | |

`SessionController` (`/sessions`): `GET /sessions/{token}` (`404 SESSION_NOT_FOUND (1060)`, `410 SESSION_EXPIRED (1061)`, `400 SESSION_INVALID_TOKEN (1062)`) and `GET /sessions/{token}/validate` → `{valid: boolean}`. Token = gzip-compressed transaction JSON, base64url-encoded (`TokenUtils`).

## 6. Validations & Error Codes

### Credential / password rules
- `LoginRequest`: `email` `@NotBlank @Email`, `password` `@NotBlank`.
- Passwords **AES/GCM encrypted (reversible), not one-way hashed** (`CryptoUtil`, key = `SHA-256(cryptoProperties.secretKey)`, default `"default-secret-key-change-in-production"`). Login compares decrypted value.
- Generated passwords: 16 alphanumeric chars from `SecureRandom` (`PasswordUtil`). No complexity/rotation policy.
- `UpdatePasswordRequest`: both fields `@NotBlank`.

### Token validation
- Signature (HMAC), `iss`/`aud` required-match, `exp`, plus `token_type` check and **DB active check**. Expired-but-present access tokens lazily flipped to `EXPIRED`.

### Error codes (`fynxt.common.enums.ErrorCode`) relevant to auth
| Code | Constant | Message | HTTP |
|------|----------|---------|------|
| 1005 | `FORBIDDEN` | Access forbidden | 403 |
| 1008 | `INVALID_CREDENTIALS` | Invalid credentials | 401 |
| 1011 | `AUTH_INVALID_CREDENTIALS` | Invalid credentials | 401 |
| 1012 | `AUTH_INSUFFICIENT_PERMISSIONS` | Insufficient permissions | 403 |
| 1013 | `AUTHENTICATION_REQUIRED` | Authentication required | 401 |
| 1014 | `INVALID_TOKEN` | Invalid token | 401 |
| 1015 | `SECRET_TOKEN_INVALID` | Invalid secret token | 401 |
| 1016 | `AUTHENTICATION_FAILED` | Authentication failed | 500 |
| 1035–1038 | `USER_NOT_FOUND`, `USER_ALREADY_EXISTS`, `USER_PASSWORD_TOO_WEAK`, `USER_NO_ACCESS` | | 401/409/500/403 |

## 7. Frontend Integration

### 7.1 Token storage — `frontend/src/store/auth.store.ts`
Zustand store with `persist`, key **`"auth-storage"`** (localStorage). Persists `accessToken`, `refreshToken`, `expiresAt`, `refreshTokenExpiresAt`, `isAuthenticated`, `user`. Helpers: `isTokenExpired()`, `isRefreshTokenExpired()`, scope predicates `isSystemUser/isBrandUser/isFIUser`, impersonation/admin-panel flags.

### 7.2 Attaching credentials — `frontend/src/api/axios-instance.ts`
Two axios instances share `baseURL` (`VITE_API_BASE_URL`, default `https://api.nexxus.fynxt.io/nexxus/v1`):
- `apiClient` (authenticated): request interceptor injects `Authorization: Bearer <accessToken>` plus tenant headers `X-BRAND-ID`/`X-ENV-ID` from `brand-environment.store` (only if valid UUIDs).
- `publicApiClient`: only brand/env headers (login/refresh, `isPublic:true`).

### 7.3 401 handling & refresh — `frontend/src/api/auth-interceptor.ts`
Response interceptor → `AuthInterceptorService.handleAuthError`:
- Only acts on **401**. For auth endpoints it immediately `redirectToLogin()`.
- Otherwise single-flight refresh: first 401 sets `_retry`, calls `refreshAccessToken()`; concurrent 401s queued (`failedQueue`) and replayed with the new token. On refresh failure → `resetAuth()` + `window.location.href = "/login"`.
- **403 is not intercepted** — permission-denied bubbles to the caller/toast.

`refreshAccessToken` (`utils/auth.ts`): POSTs `publicApiClient` `/auth/token/refresh?refreshToken=...`, accepts codes `["200","0000"]`, `updateTokens`, keeps old refresh token if server returns none. `logoutUser` POSTs `/auth/logout`, then `resetAuth()` regardless.

### 7.4 Route guards — `frontend/src/utils/auth-guard.ts` (TanStack Router)
- `requireAuth()`: redirects to `/login` if not authenticated. SYSTEM/FI users not impersonating are confined to `/onboard` and `/brands/list`; impersonating pushes them off `/brands/list`.
- `requireNoAuth()`: bounces authenticated users away from login.
- `AuthProvider` (`context/auth-context.tsx`) rehydrates and silently refreshes if access token expired but refresh still valid.

### 7.5 Login page — `frontend/src/pages/login/login.tsx`
Calls `AuthService.login({email,password})`, then `login(accessToken, refreshToken, expiresAt, userData)` where `userData` derived from `response.data.claims`. Redirects: SYSTEM/FI → `/onboard`; BRAND → `/onboard` if >1 accessible brand else dashboard `/`.

Endpoint map (`api/endpoints.ts`): `AUTH.LOGIN=/auth/login`, `AUTH.REFRESH=/auth/token/refresh`, `AUTH.LOGOUT=/auth/logout`, `PERMISSIONS.MODULES=/permissions/modules`, `BRAND_ROLES.*=/brand-roles`, `BRAND_USERS.*=/brand-users`.

## 8. Use Cases (end-to-end traces)

### 8.1 User login
`login.tsx` → `AuthService.login` (publicApiClient POST `/auth/login`) → `AuthController.login` → `AuthServiceImpl.login` → `BrandUserAuthenticationServiceImpl.authenticateUser` (`findByEmail` + `CryptoUtil.decrypt` compare) → scope resolution (FI vs BRAND) → `JwtExecutor.generateToken` ×2 → `saveTokens` (INSERT into `tokens`) → `AuthResponse` → frontend stores tokens + user in `auth-storage`, redirects by scope.

### 8.2 Authenticated request (e.g. list brand roles)
`BrandRolesService.getBrandRoles` → `apiClient` GET `/brand-roles` with Bearer + `X-BRAND-ID` + `X-ENV-ID` → `AccessTokenOncePerRequestFilter` → `JwtAuthenticationStrategy.validate` (JWT verify + `token_type=ACCESS` + `countActiveToken`) sets `jwt.claims`/`jwt.subject` → `BrandEnvironmentContextFilter` builds thread-local context, resolves `roleId` for header brand/env, loads `rolePermissions` → `ScopeCheckAspect` (scope ∈ {FI,BRAND}) → `PermissionCheckAspect` (`brand_roles:read`; FI passes free, BRAND checks JSON map) → controller → `BrandRoleServiceImpl.readAll(brandId, envId)`.

### 8.3 Permission denied
Same path; `validateBrandPermission` finds `read` not in `rolePermissions["brand_roles"].actions` → `PermissionDeniedException` → `AUTH_INSUFFICIENT_PERMISSIONS (1012)` / HTTP **403**. Frontend surfaces via toast (403 not auto-refreshed/redirected).

### 8.4 Token refresh (expired access token)
Any authenticated request returns **401 TOKEN_VALIDATION_FAILED** → interceptor marks `_retry`, calls `refreshAccessToken` → POST `/auth/token/refresh?refreshToken=…` → `refreshToken` (validate refresh JWT + DB active) → mints new access token, `revokeAccessTokensForUser` + `saveToken`, returns same refresh token → store `updateTokens` → queued requests replayed. Refresh token expired/invalid → `resetAuth()` + redirect `/login`.

### 8.5 Logout
`logout` → `logoutUser` → POST `/auth/logout` (Bearer) → `AuthServiceImpl.logout` extracts `user_id`, `revokeAllTokensForUser` (all `tokens` → `REVOKED`) → frontend `resetAuth()`, `window.location.href="/login"`. Old JWT then fails the DB active check even though signature/exp still valid.

## 9. Notable observations
- Passwords stored **reversibly encrypted (AES/GCM)** and compared by decryption — atypical for credential storage.
- HMAC token-binding key and JWT signing-key derivation use **hard-coded string constants**; secrecy depends only on the `keyId`/config values, and `CryptoUtil` falls back to a default secret key if unset.
- Refresh does **not rotate** the refresh token.
- `X-BRAND-ID`/`X-ENV-ID` are client-supplied and select which role/permissions apply; the server cross-checks them against the JWT `accessible_brands` structure to resolve `roleId` (a brand/env not in the claim → `roleId=null` → no `BRAND` permissions).
